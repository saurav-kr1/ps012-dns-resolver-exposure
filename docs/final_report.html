2. Scope, method and safety rules

Scope. Recursion exposure only, on authorised lab servers, from a separate client network. Out of scope: Internet-wide scanning, spoofed traffic and amplification stress testing.

Method. For each server, three times: (P1) ask for a never-before-seen random name under our test zone with recursion desired; a correct answer proves a real lookup. (P2) if the server owns a zone, ask for it with recursion off and look for the authoritative flag. The test-zone server logs who asked, which gives an independent second proof. Attempts are combined by majority vote; a label needs more than half the votes, otherwise the server is inconclusive.

Safety rules enforced by the tool: allowlist of at most 20 private addresses; real source address only; small plain queries (no ANY, no large buffers); global limit 5 queries per second, per-target limit 1 per second, hard budget of 500 queries; isolated networks with no Internet access.

Accuracy fell to 7 of 8. The only change is t02 (the dnsmasq forwarder): its reply carries the AA flag, and without the log the tool cannot rule out that it simply hosts the zone, so it reports aa_set_unconfirmed instead of guessing. This is a safe failure: an exposure is reported as inconclusive, not as safe and not as a false certainty. The other open resolvers (t01 and t08) do not set AA, so they are still found.

5.4 Experiment B: packet loss and retries

The lossy server t08 is a genuine open resolver whose replies are dropped 20% of the time. We assessed this one server 40 times for each retry setting (still under the rate limits) and counted how often it was not labelled recursive, which is a false negative for exposure.

Retries per probeRunsLabelled recursiveNot recursive (false negative)Expected from theoryAverage queries per run
040328 (20.0%)10.40%3.0
140400 (0.0%)0.47%3.6
240400 (0.0%)0.02%3.58

How to read it. If one reply is lost with probability 0.2, a probe with n retries fails with probability 0.2n+1; with three attempts and a majority vote the expected miss rate is the "theory" column. More retries make a miss far less likely at the cost of a few extra queries per run. With 40 runs per setting the measurement is noisy: at 0 retries theory predicts about 4.2 misses (standard deviation about 1.9), and we measured 8, which is 2.0 standard deviations above that. We report the measured value as it is and do not adjust it. A larger sample would narrow the gap; the conclusion does not depend on it, because every setting with at least one retry found the open resolver in all of its runs. In the three real runs of the full assessment (2 retries), 1 of 9 t08 probes needed more than one try, and t08 was still labelled recursive every time.

5.5 An unexplained outlier

After the three documented runs we rehearsed the live demo and then ran a stability test. Of the 15 further runs with the final settings, 14 were fully correct (12 of 12 in the stability test). In one run (the first live run of the rehearsal, 20261120-103817) the lossy server t08 was labelled inconclusive instead of recursive, giving 7 of 8.

AttemptTries usedReplyLatencyLabel of this attempt
11answered1032 msrecursive (resolved+log_confirmed)
23none (timeout)-inconclusive (no_response)
33none (timeout)-inconclusive (no_response)

What the evidence shows. The first attempt resolved normally (after an unusually slow first reply). Attempts 2 and 3 each lost all 3 tries, although the test-zone log shows that the resolver did look the names up. Two such failures in a row are far less likely than 20% random loss would suggest (about 0.8% per attempt, so well under 0.01% for two), so simple packet loss is probably not the whole explanation.

What we do not know. We could not reproduce it: the next 14 runs were all correct. One possible factor is that the run started right after several containers had just been created and removed, which may briefly disturb the virtual network, but we did not confirm this and do not claim it as the cause.

Why it still matters. The tool failed in the safe direction: a real open resolver was reported as inconclusive, not as closed. An operator reading the report is told that the result is uncertain, not that the server is safe. It also illustrates why a single run is weaker evidence than repeated runs, and why the tool reports reason codes. A larger sample would give a better estimate of how often this happens.

5.6 Limitations

  • The lab is a model of real networks, and the same person built the servers and the answer key.
  • Results come from a single vantage point, so servers that are open only to some source networks could look refused.
  • Only recursion exposure is tested; nothing else about the servers' security is assessed.
  • Experiment B uses simulated loss on replies only; real networks may also drop queries or add delay.

For all networks, RFC 5358 also asks operators to deploy ingress filtering (BCP 38, or BCP 84 for multihomed networks), because blocking spoofed source addresses is the only fix for the root cause of reflection attacks.

7. Conclusion

The tool found every open resolver in the lab, correctly identified the two properly closed servers, and reported the three unclear cases honestly. Results were identical in the three documented runs and correct in 14 of 15 further runs, with one unexplained exception that failed safe (Section 5.5). The tool stayed within its rate limits, and the weak points (forwarder flags, packet loss, broken upstreams) were tested rather than assumed. The analysis shows that an inconclusive result is not the same as safe, and that the design fails toward caution.

  2. Full assessment: docker compose run --rm probe (report in results/<run>/report.md).
  3. Compare runs: python -m probe.compare results/<run1> results/<run2> results/<run3>
