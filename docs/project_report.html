1. Problem statement

Open recursive DNS resolvers answer queries from anyone on the Internet. Because DNS mostly runs over UDP, which has no handshake, an attacker can forge the source address of a query so that the resolver sends its answer to a victim. Answers can be many times larger than questions (RFC 5358 gives a factor of about 80), so a small botnet together with thousands of forgotten open resolvers can produce gigabits of unwanted traffic. This is a reflection and amplification DDoS attack.

RFC 5358 asks operators to serve recursion only to their intended clients. The practical question this project answers is: how can an operator check, precisely, reproducibly and ethically, whether a DNS server really follows that rule? Careless scanning can itself disrupt networks, so the measurement method must be bounded, repeatable and limited to authorised servers.

The task (problem statement PS-012) is to build a probing tool that tests up to 20 designated lab DNS servers from an external client, classifies each as recursive, authoritative-only, refused or inconclusive, compares the result with seeded ground truth, and enforces strict rate controls. Internet-wide scanning, spoofed traffic and amplification stress testing are explicitly out of scope.

2. Objectives

  1. Build a command-line probe tool that tests up to 20 allowlisted lab servers from a separate client vantage point.
  2. Classify every server into exactly one of the four categories, recording a reason code and evidence.
  3. Enforce configurable rate control (global and per-target limits, timeouts, retries, query budget) so every run is bounded and reproducible.
  4. Build a controlled lab with a test zone and labelled test servers, and compare results with a seeded ground truth (accuracy, confusion matrix, precision and recall).
  5. Analyse false and inconclusive results and explain their causes.
  6. Produce an exposure assessment report, a demonstration, and documented code in a repository.

3. Design of the solution

3.1 Overview and architecture

The solution has two parts: a lab (Docker) and a probe tool (Python). The lab has two isolated networks with no Internet access. The probe client sits on the client network and is therefore an outside stranger to the servers; the eight target servers and the test-zone server share the lab network. Every target has an address on both networks.

3.2 Method: probes and evidence

For each target the tool repeats the following three times and combines the results by majority vote.

  • P1, recursion probe. A TXT query for <random>.probe.lab.test with recursion desired. The name is brand new and not owned by the target, so only a server that really looked it up can return the marker text aiori-probe-ok. A fresh name also rules out cached answers.
  • P2, authority probe. If the target hosts a zone, an SOA query for that zone with recursion off; an authoritative-answer (AA) flag shows it is authoritative.
  • Independent confirmation. The test-zone server logs every question. If a target really recursed, the log shows the random name asked from the target's own lab address.

3.3 Classification logic

Rules are applied in order; the first match decides. The authority probe is checked before "refused" because a closed resolver and an authoritative-only server both answer REFUSED to a foreign name. If the AA flag is set on a recursive-looking answer (forwarders copy it from upstream), the test-zone log must confirm the lookup; otherwise the result is inconclusive.

3.4 Rate control and safety

A token bucket limits the speed and a hard budget limits the total. All settings are in config/probe.yaml, and a fingerprint of them is written into every report.

SettingValuePurpose

Safety rules enforced by the tool: allowlist of private lab addresses only; real source address (no spoofing); small plain UDP queries (no ANY, no large EDNS buffer); internal-only Docker networks so lab recursion never reaches the Internet.

4.3 Experiments on false and inconclusive results

Experiment A: the test-zone log is unavailable. Accuracy falls to 7 of 8. Only t02 (the dnsmasq forwarder) changes, to inconclusive with reason aa_set_unconfirmed: the tool cannot rule out that a server which sets the AA flag simply hosts the zone, so it does not guess. This is a safe failure.

Experiment B: packet loss and retries. The lossy resolver t08 (20% of replies dropped) was assessed 40 times per setting. With 0 retries it was missed in 8 of 40 runs; with 1 or 2 retries it was found in all 40 runs. Theory predicts about 4 misses at 0 retries; we report the measured 8 without adjustment (the sample is small).

5. Limitations and work that could not be completed

  • An unexplained outlier. In 15 further runs after the three documented ones, 14 were fully correct. In one run the lossy server t08 was labelled inconclusive instead of recursive (attempts 2 and 3 got no reply although the test-zone log shows the resolver did look the names up). We could not reproduce it and have not established the cause. It failed in the safe direction, reporting uncertainty rather than "closed".
  • Eight targets were built, not the maximum of 20. The tool supports 20; a larger lab was not built.
  • Single vantage point. A server that is open only to some source networks could look refused from the probe client. A second client network was not built.
  • Lab only. By design the tool was not run against the real Internet; the results show that the method works on known cases, not that it is 100% accurate on arbitrary networks. The same people built the servers and the answer key.
  • Scope of the test. Only recursion exposure over UDP and IPv4 was tested; no IPv6, TCP fallback or DNSSEC behaviour.
  • Experiment B used simulated loss on replies only, with 40 runs per setting; real networks may also drop queries or add delay.

7. Main observations and conclusions

  1. The tool found every open resolver in the lab, identified the two properly closed servers, and reported the three unclear cases honestly. Results were identical in three runs and stayed within the configured rate limits.
  2. Flags alone are not reliable evidence. A forwarder copies the upstream AA flag, so independent proof (the test-zone log) is needed. Without it the tool fails safe.
  3. Inconclusive does not mean safe. t07 is willing to recurse but its upstream is broken; once repaired it would answer anyone. It should be treated as potentially exposed.
  4. Retries matter. Without retries a real open resolver behind 20% packet loss was missed in a fifth of the runs; with one retry it was not missed in 40 runs. Packet loss does not protect a resolver, it only makes it harder to detect.
  5. Testing the real lab, not only unit tests, changed the design (the AA rule, the .test handling, the BIND setup).
  6. Recommended action for every exposed server follows RFC 5358: restrict recursion to the intended clients (ACL, incoming interface, signed queries, VPN), keep recursion off on authoritative-only servers, and deploy ingress filtering (BCP 38) as the only fix for the root cause.

Future work: a second client network, all 20 targets, a larger sample for the lossy case, and finding the cause of the outlier.
