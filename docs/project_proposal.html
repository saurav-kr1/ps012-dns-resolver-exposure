AIORI-3 · Cybersecurity · PS-012 · Project proposal

Authorised DNS Resolver Exposure Assessment

Saurav Kumar (264101047) & Tanay Umesh Hambire (264101057)

1. Background and problem

Open recursive DNS resolvers answer queries from anyone on the Internet. Because DNS mostly uses UDP, an attacker can forge the source address of a query so that the resolver sends a much larger answer to a victim (RFC 5358 gives an amplification factor of about 80). Thousands of forgotten open resolvers therefore let a small botnet produce gigabits of unwanted traffic in a reflection and amplification DDoS attack. RFC 5358 asks operators to serve recursion only to their intended clients.

Problem: operators need a precise, reproducible and ethical way to check whether their DNS servers follow that rule. Careless scanning can itself disrupt networks, so the method must be bounded and limited to authorised servers.

2. Objectives

  1. Build a command-line probe tool that tests up to 20 authorised lab DNS servers from a separate client vantage point.
  2. Classify each server as recursive, authoritative-only, refused or inconclusive, with a reason code.
  3. Enforce configurable rate control (global and per-target limits, timeouts, retries, query budget) so every run is bounded and reproducible.
  4. Compare the results with a seeded ground truth and analyse false and inconclusive results.

3. Proposed solution

  • Controlled lab (Docker). Two isolated networks without Internet access: a test-zone server we control (lab.test, with a query log), several target servers configured on purpose (open, ACL-restricted, interface-restricted, authoritative-only, silent, broken, lossy; using Unbound, dnsmasq and BIND), and a separate probe client acting as the outside vantage point. We know what each server really is, which gives the ground truth.
  • Two probes. P1 asks for a never-before-seen random name with recursion desired, so a correct answer proves a real lookup (no cache). P2 asks for the server's own zone with recursion off and looks for the authoritative flag, which separates an authoritative-only server from a closed resolver (both answer REFUSED to P1).
  • Independent proof. The test-zone log shows which server asked for each random name.
  • Classification and voting. A decision tree labels every attempt; three attempts per probe are combined by majority vote. Weak evidence becomes inconclusive, never a guess.
  • Rate control. A token bucket and a hard query budget keep each run bounded.
  • Evaluation. Accuracy, confusion matrix, precision and recall against the ground truth, repeated runs for reproducibility, and an analysis of false and inconclusive results.

4. Scope, ethics and constraints

In scopeOut of scope (forbidden)
Up to 20 authorised lab servers that we build and own; recursion exposure only; a controlled test zone; a separate client network; small standard queries at a bounded rate Internet-wide scanning or any server not on the allowlist; spoofed traffic (the real source address is always used); amplification or stress testing; testing anything other than recursion exposure

The tool will refuse to run if the target list has more than 20 entries or contains a public IP address.

5. Expected outcomes and deliverables

  • A DNS resolver probe tool, controlled labelled test cases, and a configurable rate-control mechanism
  • Response classification and ground-truth comparison, and a DNS exposure assessment report
  • A false/inconclusive result analysis, a technical demonstration with pseudocode, and a code repository with documentation
