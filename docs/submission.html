3. Problem Description

Open recursive DNS resolvers answer queries from anyone on the Internet. Because DNS mostly runs over UDP, which has no handshake, an attacker can forge the source address of a query so that the resolver sends its answer to a victim instead. Answers can be many times larger than questions (RFC 5358 gives a factor of about 80), so a small botnet and thousands of forgotten open resolvers can produce gigabits of unwanted traffic. This is a reflection and amplification DDoS attack.

RFC 5358 asks operators to serve recursion only to their intended clients. The practical question is: how do we check, precisely and ethically, whether a given server really follows that rule?

Key issues

  • Telling recursion from authority. A correct-looking answer can come from a server that really recursed, from one that simply hosts the zone, or from a forwarder. The tool must know which.
  • REFUSED is ambiguous. A closed resolver and an authoritative-only server both answer REFUSED to a question about a foreign name, yet they are different cases.
  • Real networks are messy. Packet loss, broken upstreams (SERVFAIL) and silent servers create weak evidence. A tool that guesses will give wrong labels.
  • Flags can mislead. Forwarders such as dnsmasq copy the upstream server's "authoritative" flag into their own replies.
  • Testing must be safe. Careless scanning can itself disrupt networks. The assessment has to be bounded, reproducible and limited to authorised lab servers.

The task (from the problem statement)

Build a reproducible probing tool that determines whether up to 20 designated lab DNS servers provide recursion to an authorised external lab client, classify each as recursive, authoritative-only, refused or inconclusive, compare the result with seeded ground truth, and enforce strict rate controls. Out of bounds: Internet-wide scanning, spoofed traffic and amplification stress testing.

4. Solution Proposed

4.1 Overview of the approach

We built a Python probe tool and a Docker-based DNS lab. The lab contains a test-zone server that we control, and eight target servers that we configured on purpose (open, restricted, authoritative-only, silent, broken, lossy). A probe client on a separate network sends small, rate-limited queries to each target. For every target the tool decides on one of the four labels and then scores itself against an answer key written when the servers were configured.

4.2 The two probes

ProbeWhat is sentWhat it proves
P1: recursion probeA TXT query for <random>.probe.lab.test with recursion desired (RD=1). The name is brand new and not owned by the target.Only a server that really looked the name up can return the marker text aiori-probe-ok. A fresh name also rules out cached answers.
P2: authority probeAn SOA query for the target's own zone with RD=0 (only if the target hosts one).An AA flag on the target's own zone shows it is authoritative.

Independent confirmation. The test-zone server logs every question. If a target really recursed, the log contains the random name from the target's own lab address. The tool checks this and reports it as log_confirmed.

5. Optimization Proposed by the Team

5.1 Optimizations and enhancements

  1. A fresh random name for every probe. A fixed name could be answered from a cache and be mistaken for fresh recursion.
  2. Test-zone log as a second, independent proof. The tool does not trust the reply alone.
  3. Authority probe checked before "refused". This separates a closed resolver from an authoritative-only server.
  4. Retries plus majority voting. One lost packet cannot change a label.
  5. Token-bucket rate control and a hard query budget. The test is bounded by design.
  6. An honest "inconclusive" class with reason codes such as no_response, servfail and aa_set_unconfirmed, instead of forced guesses.
  7. Allowlist and private-address check. The tool refuses to start if a target is public, duplicated, or if there are more than 20.
  8. Fingerprinted configuration, a dry-run mode and a run-comparison command for reproducibility.

6. Solution Architecture and Design

6.1 Architecture overview

The lab has two isolated Docker networks with no Internet access. The probe client lives on the client network (172.31.0.0/24). Every target has an address on both networks; the lab network (172.30.0.0/24) is where the targets and the test-zone server live. The client is therefore an outside stranger, which is exactly the vantage point that exposure needs.

6.3 Classification decision tree

Why the order matters: a closed resolver and an authoritative-only server both answer REFUSED to P1. Checking authority (P2) before refusal separates them. A resolver that cannot reach its upstream may return SERVFAIL even though it would recurse, so that case is recorded as inconclusive with a reason, not as "not recursive".

6.4 Pseudocode

load config and targets            # abort if more than 20, duplicates, or any public IP
for each target (every send passes the rate limiter, which also enforces the budget):
    for attempt in 1..3:
        nonce = random_label()
        r1  = query(target, nonce + ".probe.lab.test", TXT, RD=1)           # recursion probe
        r2  = query(target, target.own_zone, SOA, RD=0) if target.own_zone  # authority probe
        hit = testzone_log_has(nonce, from=target.lab_ip) if r1 answered correctly
        votes.append(classify(r1, r2, hit))
    label = majority_vote(votes)       # needs more than half, else INCONCLUSIVE
compare labels with targets.yaml  ->  accuracy, confusion matrix, mismatch analysis, report

classify(r1, r2, hit):
    if no valid r1 and no valid r2:                  return INCONCLUSIVE, "no_response"
    if r1 is NOERROR and r1.RA and r1 has marker TXT:
        if r1.AA and hit is not True:                return INCONCLUSIVE, "aa_set_unconfirmed"
        return RECURSIVE, "resolved" (+ "log_confirmed" if hit)
    if r2 and r2.AA and r2 is NOERROR:               return AUTH_ONLY, "aa_on_own_zone"
    if REFUSED in (r1.rcode, r2.rcode):              return REFUSED, "rcode_refused"
    return INCONCLUSIVE, reason(r1, r2)
Safety rules enforced in the design Only allowlisted private lab addresses (public IPs rejected), at most 20 targets, the real source address (no spoofing), small plain UDP queries (no ANY, no large EDNS buffer), global and per-target rate limits, a hard query budget, and internal-only Docker networks so lab recursion never reaches the Internet.

9. Conclusion

Summary. We built a reproducible, rate-limited tool that decides whether a DNS server provides recursion to an outside client, and tested it in a Docker lab of eight deliberately configured servers. It classified all eight correctly in three identical runs, stayed within its rate limit (peak 5 queries per second, 39 to 45 queries per run), and confirmed every open resolver with an independent proof from the test-zone log. Real-lab testing also uncovered problems that unit tests could not, such as forwarders copying the authoritative flag, and the tool was changed to handle them.

Significance. Open resolvers are the fuel for DNS amplification attacks. A safe, repeatable way to measure exposure lets operators find and close them, which is exactly what RFC 5358 asks for, without scanning anything they are not authorised to test. The honest "inconclusive" class, with reason codes, keeps the results trustworthy.

Limitations. The lab is a model of real networks. Results come from a single vantage point, so a server that is open only to some source networks could look refused from here. Only recursion exposure is tested.

Next steps. Complete the GitHub setup, finalise the exposure assessment report with the false and inconclusive result analysis, and demonstrate the tool and pseudocode to the mentor. Possible extensions are a second client network to test source-dependent restrictions and a larger target set of up to 20 servers.
